## 철학

MVP 속도 최우선. 관리 부담이 큰 자체 인프라보다 관리형 서비스(Supabase, Vercel, Polar)를
우선한다. 별도 도구 도입은 실제로 필요해지기 전까지 미룬다(에러 모니터링, 관리자 화면 등).

---

### ADR-001: 데이터베이스 & 인증 — Supabase (Postgres + Auth)

**결정**: 사용자 계정, 분석 이용 현황, 구독 상태, 분석 결과를 Supabase(Postgres)에 저장한다.
인증도 별도 라이브러리(Auth.js 등) 없이 Supabase Auth의 구글 OAuth 프로바이더로 통합한다.

**이유**: DB와 인증을 한 스택에서 관리하면 사용자별 데이터 접근 제어를 Row Level Security(RLS)로
DB 레벨에서 강제할 수 있다(F-RIRRKL "보호 화면은 인증 상태 확인" 요구사항과 직결). 관리형
서비스라 별도 인프라 운영 부담이 없다.

**트레이드오프**: Supabase에 대한 벤더 락인. 구글 외 로그인 제공자를 나중에 추가할 때도
Supabase Auth의 프로바이더 설정에 의존하게 된다.

---

### ADR-002: 배포 — Vercel

**결정**: Vercel에 배포한다.

**이유**: Next.js 공식 플랫폼이라 App Router/서버 컴포넌트와의 호환성이 검증되어 있고, 이
프로젝트에 Vercel MCP가 이미 연동되어 있어 배포/모니터링 도구 접근이 바로 가능하다.

**트레이드오프**: 서버리스 함수 실행 시간 제한이 있어 AI 분석처럼 오래 걸리는 작업은 동기 요청
안에서 처리할 수 없다 (→ ADR-006 비동기 처리로 대응).

### ADR-003: 업로드 원본 파일 보관 정책 — 24시간 임시 보관 후 자동 삭제

**결정**: 사용자가 업로드한 CSV/PDF 원본은 24시간 동안만 보관하고 이후 자동 삭제한다. 추출된
거래 내역과 분석 결과만 별도로 계속 보관한다(→ ADR-007).

**이유**: 원본 파일은 카드 거래 내역이 그대로 담긴 가장 민감한 형태의 데이터다. PRD의 Risks
("개인 금융 데이터 포함 → 파일 보안, 접근 통제, 보관/삭제 정책 미흡 시 개인정보 유출 위험")에
대응해 보관 기간을 최소화한다. 24시간은 처리 실패 시 재시도할 여유를 남기는 선에서 결정했다.

**트레이드오프**: 분석 실패 후 24시간이 지나면 사용자가 파일을 다시 업로드해야 한다.

### ADR-004: 거래 내역 추출 — LLM(Claude) 기반, 텍스트+이미지 PDF 모두 지원

**결정**: CSV/PDF에서 거래일·가맹점·금액을 추출할 때 카드사별 규칙 기반 파서를 만들지 않고,
Claude(텍스트 + Vision)에 파일을 직접 전달해 구조화된 거래 내역으로 추출한다. 텍스트 기반 PDF뿐
아니라 이미지 스캔본 PDF도 Claude Vision으로 지원한다.

**이유**: PRD Risks에서 "카드사별로 CSV/PDF 형식이 달라 데이터 추출이 실패할 수 있음"을 명시
지적했다. 카드사마다 별도 파서를 만들고 유지보수하는 대신 LLM의 일반화 능력으로 포맷 다양성에
대응한다.

**트레이드오프**: 규칙 기반 파서 대비 추출 정확도가 케이스마다 편차가 있을 수 있고, 분석당
AI 호출 비용이 추가된다(추출 1회 + 분석 1회). 스캔본 PDF는 이미지 화질에 따라 추출 실패율이
높아질 수 있다.

### ADR-005: AI 소비 분석 — Claude API, 고정 12개 카테고리, LLM 직접 판단 기반 이상 탐지

**결정**: 카테고리 분류·이상 지출 탐지·절약 추천 생성 모두 Anthropic Claude API로 수행한다.
카테고리는 아래 12개 고정 목록 중에서만 분류하며, 이상 지출 탐지는 별도 통계 로직 없이 LLM이
거래 내역 전체를 보고 직접 판단한다.

```
식비, 교통, 카페/간식, 쇼핑, 문화/여가, 의료/건강,
주거/관리비, 통신비, 교육, 여행, 구독/금융, 기타
```

**이유**: 고정 카테고리는 UI_GUIDE의 카테고리 차트 6색 순환 규칙과 대시보드 차트 UI를 안정적으로
유지하기 위해 필요하다(AI가 매번 다른 카테고리명을 생성하면 차트/색상 매핑이 깨진다). 이상 탐지를
통계 임계값 없이 LLM 판단에 맡긴 것은 MVP 구현 범위를 줄이기 위한 선택이다.

**트레이드오프**: 통계 기반 임계값이 없어 이상 탐지 결과의 판단 근거가 매번 조금씩 달라질 수
있다(일관성이 규칙 기반보다 낮음). 카테고리가 12개로 고정되어 세분화된 소비 패턴(예: "배달음식"과
"식비" 구분)은 담지 못한다.

### ADR-006: 분석 처리 방식 — 비동기(백그라운드 job + 폴링)

**결정**: 파일 업로드 → 거래 추출 → AI 분석까지 이어지는 처리는 한 HTTP 요청-응답 안에서
끝내지 않고, 백그라운드 job으로 실행하고 클라이언트가 상태를 폴링해서 진행 상태/완료를
반영한다.

**이유**: Vercel 서버리스 함수의 실행 시간 제한(ADR-002) 때문에 LLM 기반 추출 + 분석을 동기
요청 안에 넣으면 타임아웃 리스크가 크다. UI_GUIDE의 "상태를 숨기지 않는다" 원칙과도 맞물려,
진행 중 상태를 화면에 명시적으로 보여줘야 한다(F-ANJCJR).

**트레이드오프**: 동기 처리보다 구현이 복잡하다(작업 상태 저장, 폴링 엔드포인트, 폴링 주기 관리
필요). 구체적인 백그라운드 실행 메커니즘(Vercel 함수의 `waitUntil`, Supabase Edge Function,
외부 큐 서비스 등)은 이 ADR에서 확정하지 않았다 — 실제 구현 착수 시 결정한다.

### ADR-007: 분석 결과 보관 정책 및 이력 — 최신 결과만 표시, 계정 삭제 전까지 보관

**결정**: 추출된 거래 내역과 AI 분석 결과는 계정이 삭제/해지되기 전까지 계속 보관한다. 단,
대시보드는 과거 분석 이력을 목록으로 보여주지 않고 항상 최신 분석 결과만 표시한다(새 분석
완료 시 이전 결과는 덮어쓴다).

**이유**: 이력 목록 UI/데이터 모델을 만들지 않아 MVP 구현 범위를 줄인다. 결과를 계정 삭제 전까지
보관하기로 한 것은 재분석 없이 마지막 결과를 다시 볼 수 있게 하기 위함이다.

**트레이드오프**: ⚠️ **계정 삭제(탈퇴) 기능 자체가 MVP 범위 밖으로 결정되어**(사용자 인터뷰
확정 사항), 현재 정책대로면 분석 결과가 사실상 무기한 보관된다. 개인 금융 데이터를 삭제 경로
없이 계속 들고 있는 것은 PRD Risks의 "개인정보 유출 위험"과 직결되는 리스크이므로, **MVP 이후
가장 먼저 재검토할 항목**으로 남긴다(계정 삭제 기능 추가 또는 별도 보관 기간 상한 설정 필요).
이력이 없으므로 사용자는 과거 분석을 다시 볼 방법이 없다(새로 분석해야 함).

### ADR-008: 결제 — Polar, 샌드박스 우선 검증, 월 ₩9,900

**결정**: 구독 결제는 Polar로 처리하며, 개발/검증 단계에서는 Polar 샌드박스(테스트) 환경으로
먼저 결제 플로우를 검증한 뒤 프로덕션 키로 전환한다. 구독가는 월 ₩9,900로 확정하고 랜딩
페이지에 공개한다.

**이유**: PRD Product Decisions에서 Polar 연동은 이미 확정되어 있었고, 실제 결제 검증 전에
샌드박스로 웹훅/구독 상태 갱신 로직을 안전하게 테스트하기 위함이다. 가격은 UI_GUIDE 프로토타입에
예시로 쓰인 값을 그대로 실제 가격으로 채택했다.

**트레이드오프**: 샌드박스 → 프로덕션 전환 시 Polar 상품/가격 ID를 다시 설정해야 하는 절차가
추가된다.

### ADR-009: 운영 도구 — 관리자 화면 미구현 / Vercel 기본 로그 / PostHog 제품 분석 도입

**결정**: MVP에서는 별도 관리자(Admin) 화면을 만들지 않고 Supabase 대시보드에서 DB를 직접
조회해 운영한다. 에러 모니터링(Sentry 등)도 별도로 도입하지 않고 Vercel 기본 로그만 사용한다.
반면 제품 분석 도구로는 PostHog를 도입한다.

**이유**: PRD에서 관리자 기능은 "최소"로만 언급되어 있어 별도 화면 구현보다 DB 직접 조회가
MVP 속도에 유리하다. 에러 모니터링도 초기에는 Vercel 로그로 충분하다고 판단했다. 다만
PostHog는 PRD Success Metrics(랜딩→가입→업로드→분석 전환율, 무료→유료 전환율 등)를 측정하는 데
필수적이고, 이 프로젝트에 PostHog MCP가 이미 연동되어 있어 도입 비용이 낮다.

**트레이드오프**: 결제/AI 분석처럼 비동기 실패가 잦을 수 있는 서비스 특성상, 구조화된 에러
추적 없이는 장애 파악이 Vercel 로그 확인에 의존하게 되어 운영 부담이 있을 수 있다. 필요해지면
재검토한다.
