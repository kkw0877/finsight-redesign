## 철학

MVP 속도 최우선. 관리 부담이 큰 자체 인프라보다 관리형 서비스(Supabase, Vercel, Polar)를
우선한다. 별도 도구 도입은 실제로 필요해지기 전까지 미룬다(에러 모니터링, 관리자 화면 등).

---

### ADR-001: 데이터베이스 & 인증 — Supabase (Postgres + Auth)

**결정**: 사용자 계정, 분석 이용 현황, 구독 상태, 분석 결과를 Supabase(Postgres)에 저장한다.
인증도 별도 라이브러리(Auth.js 등) 없이 Supabase Auth의 구글 OAuth 프로바이더로 통합한다.

**이유**: DB와 인증을 한 스택에서 관리하면 사용자별 데이터 접근 제어를 Row Level Security(RLS)로
DB 레벨에서 강제할 수 있다(F-RIRRKL "보호 화면은 인증 상태 확인" 요구사항과 직결). 관리형
서비스라 별도 인프라 운영 부담이 없다.

**트레이드오프**: Supabase에 대한 벤더 락인. 구글 외 로그인 제공자를 나중에 추가할 때도
Supabase Auth의 프로바이더 설정에 의존하게 된다.

---

### ADR-002: 배포 — Vercel

**결정**: Vercel에 배포한다.

**이유**: Next.js 공식 플랫폼이라 App Router/서버 컴포넌트와의 호환성이 검증되어 있고, 이
프로젝트에 Vercel MCP가 이미 연동되어 있어 배포/모니터링 도구 접근이 바로 가능하다.

**트레이드오프**: 서버리스 함수 실행 시간 제한이 있어 AI 분석처럼 오래 걸리는 작업은 동기 요청
안에서 처리할 수 없다 (→ ADR-006 비동기 처리로 대응).

### ADR-003: 업로드 원본 파일 보관 정책 — 24시간 임시 보관 후 자동 삭제

**결정**: 사용자가 업로드한 CSV/PDF 원본은 24시간 동안만 보관하고 이후 자동 삭제한다. 추출된
거래 내역과 분석 결과만 별도로 계속 보관한다(→ ADR-007).

**이유**: 원본 파일은 카드 거래 내역이 그대로 담긴 가장 민감한 형태의 데이터다. PRD의 Risks
("개인 금융 데이터 포함 → 파일 보안, 접근 통제, 보관/삭제 정책 미흡 시 개인정보 유출 위험")에
대응해 보관 기간을 최소화한다. 24시간은 처리 실패 시 재시도할 여유를 남기는 선에서 결정했다.

**트레이드오프**: 분석 실패 후 24시간이 지나면 사용자가 파일을 다시 업로드해야 한다.

### ADR-004: 거래 내역 추출 — LLM(Claude) 기반, 텍스트+이미지 PDF 모두 지원

**결정**: CSV/PDF에서 거래일·가맹점·금액을 추출할 때 카드사별 규칙 기반 파서를 만들지 않고,
Claude(텍스트 + Vision)에 파일을 직접 전달해 구조화된 거래 내역으로 추출한다. 텍스트 기반 PDF뿐
아니라 이미지 스캔본 PDF도 Claude Vision으로 지원한다. CSV는 UTF-8뿐 아니라 국내 카드사
내보내기에 흔한 EUC-KR/CP949 인코딩도 자동 감지해 처리한다. 추출 결과에는 거래일·가맹점명·
금액·거래 유형만 담고, 카드번호·계좌번호 등 결제수단 식별자는 추출하지 않는다(데이터 최소화).

**이유**: PRD Risks에서 "카드사별로 CSV/PDF 형식이 달라 데이터 추출이 실패할 수 있음"을 명시
지적했다. 카드사마다 별도 파서를 만들고 유지보수하는 대신 LLM의 일반화 능력으로 포맷 다양성에
대응한다.

**트레이드오프**: 규칙 기반 파서 대비 추출 정확도가 케이스마다 편차가 있을 수 있고, 분석당
AI 호출 비용이 추가된다(추출 1회 + 분석 1회). 스캔본 PDF는 이미지 화질에 따라 추출 실패율이
높아질 수 있다. 인코딩 자동 감지가 실패하는 드문 케이스에서는 가맹점명이 깨져 보일 수 있다.

### ADR-005: AI 소비 분석 — Claude API, 고정 12개 카테고리, LLM 직접 판단 기반 이상 탐지

**결정**: 카테고리 분류·이상 지출 탐지·절약 추천 생성 모두 Anthropic Claude API로 수행한다.
카테고리는 아래 12개 고정 목록 중에서만 분류하며, 이상 지출 탐지는 별도 통계 로직 없이 LLM이
거래 내역 전체를 보고 직접 판단한다.

```
식비, 교통, 카페/간식, 쇼핑, 문화/여가, 의료/건강,
주거/관리비, 통신비, 교육, 여행, 구독/금융, 기타
```

**이유**: 고정 카테고리는 UI_GUIDE의 카테고리 차트 6색 순환 규칙과 대시보드 차트 UI를 안정적으로
유지하기 위해 필요하다(AI가 매번 다른 카테고리명을 생성하면 차트/색상 매핑이 깨진다). 이상 탐지를
통계 임계값 없이 LLM 판단에 맡긴 것은 MVP 구현 범위를 줄이기 위한 선택이다.

**트레이드오프**: 통계 기반 임계값이 없어 이상 탐지 결과의 판단 근거가 매번 조금씩 달라질 수
있다(일관성이 규칙 기반보다 낮음). 카테고리가 12개로 고정되어 세분화된 소비 패턴(예: "배달음식"과
"식비" 구분)은 담지 못한다.

### ADR-006: 분석 처리 방식 — 비동기(백그라운드 job + 폴링)

> **상태**: ADR-017로 대체됨(동기 처리로 전환). 아래 내용은 결정 배경 기록용으로 남겨둔다.

**결정**: 파일 업로드 → 거래 추출 → AI 분석까지 이어지는 처리는 한 HTTP 요청-응답 안에서
끝내지 않고, 백그라운드 job으로 실행하고 클라이언트가 상태를 폴링해서 진행 상태/완료를
반영한다.

**이유**: Vercel 서버리스 함수의 실행 시간 제한(ADR-002) 때문에 LLM 기반 추출 + 분석을 동기
요청 안에 넣으면 타임아웃 리스크가 크다. UI_GUIDE의 "상태를 숨기지 않는다" 원칙과도 맞물려,
진행 중 상태를 화면에 명시적으로 보여줘야 한다(F-ANJCJR).

**트레이드오프**: 동기 처리보다 구현이 복잡하다(작업 상태 저장, 폴링 엔드포인트, 폴링 주기 관리
필요). 구체적인 백그라운드 실행 메커니즘(Vercel 함수의 `waitUntil`, Supabase Edge Function,
외부 큐 서비스 등)은 이 ADR에서 확정하지 않았다 — 실제 구현 착수 시 결정한다.

### ADR-007: 분석 결과 보관 정책 및 이력 — 최신 결과만 표시, 계정 삭제 전까지 보관

**결정**: 추출된 거래 내역과 AI 분석 결과는 계정이 삭제/해지되기 전까지 계속 보관한다. 단,
대시보드는 과거 분석 이력을 목록으로 보여주지 않고 항상 최신 분석 결과만 표시한다(새 분석
완료 시 이전 결과는 덮어쓴다).

**이유**: 이력 목록 UI/데이터 모델을 만들지 않아 MVP 구현 범위를 줄인다. 결과를 계정 삭제 전까지
보관하기로 한 것은 재분석 없이 마지막 결과를 다시 볼 수 있게 하기 위함이다.

**트레이드오프**: ⚠️ **계정 삭제(탈퇴) 기능 자체가 MVP 범위 밖으로 결정되어**(사용자 인터뷰
확정 사항), 현재 정책대로면 분석 결과가 사실상 무기한 보관된다. 개인 금융 데이터를 삭제 경로
없이 계속 들고 있는 것은 PRD Risks의 "개인정보 유출 위험"과 직결되는 리스크이므로, **MVP 이후
가장 먼저 재검토할 항목**으로 남긴다(계정 삭제 기능 추가 또는 별도 보관 기간 상한 설정 필요).
이력이 없으므로 사용자는 과거 분석을 다시 볼 방법이 없다(새로 분석해야 함).

### ADR-008: 결제 — Polar, 샌드박스 우선 검증, 월 ₩9,900

**결정**: 구독 결제는 Polar로 처리하며, 개발/검증 단계에서는 Polar 샌드박스(테스트) 환경으로
먼저 결제 플로우를 검증한 뒤 프로덕션 키로 전환한다. 구독가는 월 ₩9,900로 확정하고 랜딩
페이지에 공개한다.

**이유**: PRD Product Decisions에서 Polar 연동은 이미 확정되어 있었고, 실제 결제 검증 전에
샌드박스로 웹훅/구독 상태 갱신 로직을 안전하게 테스트하기 위함이다. 가격은 UI_GUIDE 프로토타입에
예시로 쓰인 값을 그대로 실제 가격으로 채택했다.

**트레이드오프**: 샌드박스 → 프로덕션 전환 시 Polar 상품/가격 ID를 다시 설정해야 하는 절차가
추가된다.

### ADR-009: 운영 도구 — 관리자 화면 미구현 / Vercel 기본 로그 / PostHog 제품 분석 도입

**결정**: MVP에서는 별도 관리자(Admin) 화면을 만들지 않고 Supabase 대시보드에서 DB를 직접
조회해 운영한다. 에러 모니터링(Sentry 등)도 별도로 도입하지 않고 Vercel 기본 로그만 사용한다.
반면 제품 분석 도구로는 PostHog를 도입한다.

**이유**: PRD에서 관리자 기능은 "최소"로만 언급되어 있어 별도 화면 구현보다 DB 직접 조회가
MVP 속도에 유리하다. 에러 모니터링도 초기에는 Vercel 로그로 충분하다고 판단했다. 다만
PostHog는 PRD Success Metrics(랜딩→가입→업로드→분석 전환율, 무료→유료 전환율 등)를 측정하는 데
필수적이고, 이 프로젝트에 PostHog MCP가 이미 연동되어 있어 도입 비용이 낮다.

**트레이드오프**: 결제/AI 분석처럼 비동기 실패가 잦을 수 있는 서비스 특성상, 구조화된 에러
추적 없이는 장애 파악이 Vercel 로그 확인에 의존하게 되어 운영 부담이 있을 수 있다. 필요해지면
재검토한다.

### ADR-010: 비동기 분석 job 트리거 — Supabase Database Webhook + Edge Function

> **상태**: ADR-017로 대체됨(동기 처리로 전환, Edge Function 트리거 제거). 아래 내용은 결정
> 배경 기록용으로 남겨둔다.

**결정**: `analysis_jobs` 테이블에 row가 insert되면 Supabase Database Webhook이 Supabase Edge
Function을 자동 호출하고, 그 Edge Function 안에서 Claude API(거래 추출 → 소비 분석)를 호출한다.
Vercel 함수 안에서 직접 백그라운드로 처리하거나 외부 큐 서비스를 쓰지 않는다.

**이유**: ADR-006에서 비동기 처리로 정하며 "구체적인 실행 메커니즘은 미정"으로 남겨뒀던 부분을
확정한다. DB/인증으로 이미 Supabase를 쓰고 있으므로(ADR-001) 새 벤더를 추가하지 않고 해결할 수
있고, Vercel 서버리스 함수의 실행시간 제한(ADR-002)과 완전히 분리된다. MVP 규모(사용자당 월
최대 4회)에서 외부 큐 서비스의 재시도/관측성 이점은 상대적으로 작다.

**트레이드오프**: 로직이 Vercel(API 라우트)과 Supabase(Edge Function) 두 실행 환경에 걸쳐
있어, 로컬 개발 시 Supabase CLI로 Edge Function을 별도 구동해야 한다. Edge Function도 자체
실행시간 제한이 있어 매우 큰 PDF는 여전히 타임아웃 위험이 있다.

### ADR-011: 업로드 원본 파일 자동 삭제 — Supabase pg_cron

**결정**: Supabase `pg_cron` 확장으로 주기 실행되는 정리 job이, `analysis_jobs.file_expires_at`
(업로드 후 24시간, ADR-003)이 지났고 **동시에 해당 job이 `processing` 상태가 아닌**(이미
완료·실패했거나 ADR-017의 지연 확인으로 실패 처리된) 건의 Storage 오브젝트와 그 참조만
삭제한다. 아직 처리 중인 job의 파일은 그 주기에서 건너뛰고 다음 주기에 다시 판정한다.

**이유**: Postgres 확장 기능이라 별도 인프라(Vercel Cron 등)를 추가하지 않고 이미 선택한
Supabase 안에서 해결된다. 삭제 대상 판정(만료 시각 비교)과 삭제 실행이 같은 DB 트랜잭션
경계 안에 있어 일관성 관리가 쉽다. 상태 조건을 추가한 이유는, 업로드 후 24시간에 가깝게
분석 요청이 들어와 처리 중인 파일을 요청 처리 도중 pg_cron이 지워버리는 경합을 막기 위함이다.

**트레이드오프**: pg_cron 스케줄 주기(예: 매시간)만큼 실제 삭제가 지연될 수 있다 — "정확히
24시간"이 아니라 "24시간 + 최대 스케줄 주기"가 실제 보관 상한이 된다. 동기 처리(ADR-017)로
바뀌면서 `processing` 상태는 최대 타임아웃 예산(300초) 안에서만 유지되므로, 경합 가능성 자체가
ADR-006/010 시절보다 훨씬 작아졌다.

### ADR-012: 결제 확정 신뢰 소스 — Polar 웹훅

**결정**: Polar 웹훅(`checkout.completed`/`subscription.*` 이벤트)을 구독 상태 갱신의 유일한
신뢰 소스로 삼는다. 서명을 검증하고, `webhook_events` 테이블에 이벤트 ID를 기록해 중복 수신을
무시한다(idempotency). 결제 완료 후 사용자를 돌려보내는 리다이렉트 콜백은 UX(즉시 완료 화면
표시) 목적으로만 쓰고, 구독 상태 확정에는 쓰지 않는다. 결제 시작/성공/실패 같은 시도 단위
이벤트는 DB에 별도 테이블로 남기지 않고 PostHog 이벤트로 기록한다(ADR-009) — `subscriptions`/
`webhook_events`는 항상 최신·확정 상태만 담는다. 이 라우트는 다른 API와 달리 로그인 세션이
아니라 Polar 웹훅 서명으로만 인증한다 — 세션 인증 미들웨어를 다른 라우트에 일괄 적용하는 변경을
할 때 이 라우트를 예외 처리해야 한다(ARCHITECTURE.md의 API 인터페이스 표 "인증" 열 참고).

**이유**: 사용자가 결제 완료 직후 브라우저를 닫거나 리다이렉트가 실패해도 웹훅은 Polar 쪽에서
독립적으로 재시도되므로 구독 상태 데이터 정합성이 리다이렉트 방식보다 훨씬 안정적이다. Polar
공식 연동 방식이기도 하다.

**트레이드오프**: 웹훅 수신 지연이 있으면 결제 직후 화면에서 구독 상태가 잠깐 "처리 중"으로
보일 수 있다(F-PAOWJD의 "갱신 중이면 마지막 확정 상태 또는 갱신 중 상태 표시" 규칙으로 흡수).
웹훅 엔드포인트 자체의 가용성이 중요해진다.

### ADR-013: 동시 분석 요청 방지 — DB 부분 유니크 인덱스

**결정**: `analysis_jobs` 테이블에 `user_id`에 대한 부분 유니크 인덱스를
(`WHERE status = 'processing'`) 걸어, 사용자당 진행 중인 job이 DB 레벨에서 항상 1개 이하로
강제되게 한다. (동기 처리로 전환하며 status는 `processing`/`completed`/`failed` 3가지로
단순화됨 — ADR-017 참고.)

**이유**: 동일 사용자가 두 개의 분석 요청을 거의 동시에 보내는 경우, 애플리케이션 레벨에서
"기존 job이 있는지 조회 후 분기"하는 방식만으로는 두 요청이 그 조회 시점 사이에 끼어들어 레이스
컨디션으로 둘 다 통과할 수 있다. DB 제약은 두 트랜잭션 중 하나를 확정적으로 실패시켜 이 문제를
근본적으로 막는다.

**트레이드오프**: 중복 요청 시 애플리케이션은 DB의 유니크 제약 위반 에러를 잡아서 "이미 처리
중" 사용자 메시지로 변환해줘야 한다(에러 매핑 로직 필요).

### ADR-014: 업로드 파일 저장소 접근 통제 — 비공개 버킷 + Signed URL

**결정**: 업로드 원본 파일(CSV/PDF)을 담는 Supabase Storage 버킷은 비공개(private)로 설정한다.
파일에 접근할 수 있는 유일한 경로는 서버(API 라우트)가 service role 키로 생성하는
단기 유효 signed URL이며, 발급 전 요청자의 `auth.uid()`가 해당 파일의 소유자
(`analysis_jobs.user_id`)와 일치하는지 항상 확인한다. 클라이언트가 Storage 경로나 공개 URL을
직접 구성해 접근할 수 없다.

**이유**: 카드 내역서 원본은 시스템 전체에서 가장 민감한 데이터다(PRD Risks의 "파일 보안" 항목).
버킷이 공개거나 URL만 알면 누구나 접근 가능하면, 경로 추측이나 URL 유출만으로 타인의 카드 내역이
노출된다.

**트레이드오프**: signed URL 발급 로직(만료 시간, 소유자 검증)을 모든 접근 지점에서 빠짐없이
구현해야 한다 — 한 곳이라도 빠뜨리면 이 보호가 무력화된다.

### ADR-015: 개인정보 국외 이전 및 처리방침 고지

**결정**: 카드 내역(개인 금융정보)이 분석을 위해 미국 소재 Anthropic API로 전송되므로, 랜딩
페이지와 회원가입 화면에 개인정보처리방침 링크와 "AI 분석을 위해 개인정보가 국외(Anthropic,
미국)로 이전됩니다"라는 고지를 노출한다. 실제 개인정보처리방침/이용약관 문서 작성과 법적 검토는
이번 설계 범위 밖으로 두고, 구현 착수 전 별도로 진행한다.

**이유**: 개인정보보호법상 개인정보의 국외 이전은 별도 고지·동의가 필요할 수 있다. 카드 내역이라는
민감한 금융 데이터를 다루는 서비스이므로 이 고지를 누락하면 법적 리스크가 크다.

**트레이드오프**: 법무 검토 없이 "고지가 필요하다"는 사실과 노출 위치만 문서에 남겨뒀다 — 실제
문구와 동의 플로우는 구현 착수 전 확정해야 하는 선행 작업으로 남는다. 이 ADR만으로 법적 요건이
충족되는 것은 아니다.

### ADR-016: 정체된(stuck) 분석 job 타임아웃 및 재수거

> **상태**: ADR-017로 대체됨(별도 pg_cron 재수거 대신 다음 요청 시점 지연 확인으로 전환). 아래
> 내용은 결정 배경 기록용으로 남겨둔다.

**결정**: Supabase `pg_cron`으로 주기 실행되는 별도 정리 job이, `updated_at` 기준 일정 시간
(예: 10분) 이상 `pending`/`extracting`/`analyzing` 상태에 머물러 있는 `analysis_jobs` row를
`failed`로 전환하고 `error_message`에 "처리 시간 초과"를 기록한다.

**이유**: ADR-010의 Edge Function 트리거가 실패하거나 크래시하면 job이 영원히 대기 상태로 남을
수 있다. ADR-013의 부분 유니크 인덱스 때문에 이 상태에서는 해당 사용자가 새 분석을 영원히 시작할
수 없게 잠기므로, 자동으로 실패 처리해 락을 풀어주는 장치가 반드시 필요하다. 이미 ADR-011에서
pg_cron을 쓰고 있으므로 같은 패턴을 재사용한다.

**트레이드오프**: 타임아웃 값을 너무 짧게 잡으면 정상적으로 오래 걸리는 분석(큰 PDF)이 조기에
실패 처리될 수 있고, 너무 길게 잡으면 사용자가 그만큼 오래 잠겨 있는다 — 실제 Claude 처리 시간
분포를 보고 값을 조정해야 한다. 실패 처리되어도 무료/구독 횟수는 차감되지 않으므로(F-ILHNGA)
악용 여지는 적다.

### ADR-017: 분석 처리 방식 재검토 — 동기 처리로 전환 (ADR-006/010/016 대체)

**결정**: 파일 추출부터 AI 분석까지를 하나의 동기 API 요청(`POST /api/analysis/start`) 안에서
끝내고 결과를 바로 응답으로 반환한다. Vercel Route Handler의 `maxDuration`을 300초로 설정한다.
Supabase Database Webhook/Edge Function 트리거(ADR-010), 별도 job 상태 폴링 엔드포인트,
pg_cron 기반 stuck job 재수거(ADR-016)를 모두 제거한다. 클라이언트는 요청이 끝날 때까지 단일
스피너로 대기 상태를 표시한다.

동시 요청 방지(ADR-013)는 유지하되, `analysis_jobs.status`는 `processing`/`completed`/
`failed` 3가지로 단순화한다 — `pending`/`extracting`/`analyzing` 구분은 다단계 트리거 체인
때문에 필요했던 것으로, 한 요청 안에서 끝나는 동기 처리에서는 의미가 없다. 드물게 함수가
타임아웃/크래시로 중간에 죽어 `processing` 상태로 멈은 job은, **별도 스케줄 job 없이** 다음
분석 요청 시점에 지연 확인(lazy check)한다 — 기존 `processing` row의 `updated_at`이 타임아웃
예산(300초)보다 오래됐으면 그 자리에서 `failed`로 전환하고 새 요청을 진행한다.

**이유**: MVP 규모(사용자당 월 최대 4회)에서 Edge Function/웹훅/폴링/재수거 cron까지 갖춘
비동기 아키텍처는 "Vercel 함수 타임아웃이 걸릴 수 있다"는 검증되지 않은 가정 하나를 막기 위해
너무 많은 인프라를 미리 만든 것이었다 — ADR.md 철학("별도 도구 도입은 실제로 필요해지기 전까지
미룬다")과 어긋난다는 자체 검토(오버엔지니어링 리뷰)에서 지적되어 재결정했다. Vercel Fluid
Compute로 300초까지 확보하면 대부분의 카드 내역서 처리는 충분히 끝날 것으로 예상되고, 로컬
개발도 Next.js 서버 하나만 띄우면 된다(Edge Function 별도 구동 불필요 — ADR-010의 트레이드오프로
지적됐던 문제가 해소됨).

**트레이드오프**: 매우 큰 스캔본 PDF 등 예외적으로 300초를 넘는 케이스는 타임아웃 실패로
처리된다 — 사용자는 재시도해야 하지만, 실패 처리이므로 무료/구독 횟수는 차감되지 않는다
(F-ILHNGA). 실제 Claude 처리 시간을 측정해본 적이 없으므로, 구현 착수 후 실측치로
`maxDuration`을 재조정해야 할 수 있다. 세분화된 진행 상태("추출 중"/"분석 중")를 화면에 보여줄
수 없고 단일 스피너로만 표시된다 — 추후 필요해지면 스트리밍 응답(SSE)으로 개선할 수 있다.
사용량이 늘어 실제로 타임아웃이 잦아지면 이 ADR을 재검토하고 비동기로 다시 전환해야 한다.
